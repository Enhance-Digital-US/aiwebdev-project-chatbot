# chat-api Specification

## Purpose

The single backend endpoint that accepts a chat conversation, runs it against a selected model with tools, skills and guardrails, and streams the reply back to the client.

## Requirements

### Requirement: Single streaming chat endpoint
The backend SHALL expose `POST /api/chat`, accepting a JSON body `{ messages, model?, id? }` where `messages` is an array of AI SDK UI messages, and SHALL respond with an AI SDK UI message stream (Server-Sent Events).

#### Scenario: Valid chat request
- **WHEN** a client posts `{ "messages": [<user message>] }` to `/api/chat`
- **THEN** the response is a UI message stream whose text parts contain the assistant reply

#### Scenario: No other API routes
- **WHEN** a client requests any other path under `/api/`
- **THEN** the backend does not serve a chat response for it

### Requirement: Model selection with default
The endpoint SHALL use the model named by `model` from the model registry, and SHALL default to `gpt-4o-mini` when `model` is omitted.

#### Scenario: Model omitted
- **WHEN** a request has no `model` field
- **THEN** the reply is generated by `gpt-4o-mini`

#### Scenario: Known model requested
- **WHEN** a request sets `model` to `gemma4:12b`
- **THEN** the reply is generated by the local Ollama `gemma4:12b` model

### Requirement: Unknown model rejected
The endpoint MUST respond with HTTP 400 and a JSON body `{ "error": "Unknown model: <id>" }` when `model` names a model that is not in the registry, and MUST NOT start a stream.

#### Scenario: Unknown model id
- **WHEN** a request sets `model` to `does-not-exist`
- **THEN** the response status is 400 and the body is `{ "error": "Unknown model: does-not-exist" }`

### Requirement: Model registry
The backend SHALL keep a registry of models keyed by model ID. Each entry SHALL define how to create the model and MAY define provider options, whether reasoning is streamed, whether tools are supported, and a telemetry function ID. Adding a model SHALL require only a new registry entry.

#### Scenario: Registered models
- **WHEN** the registry is inspected
- **THEN** it contains `gpt-4o-mini` (OpenAI) and `gemma4:12b` (Ollama, reasoning enabled)

### Requirement: Reasoning streamed for reasoning models
For models whose registry entry enables reasoning, the stream SHALL include reasoning parts alongside text parts. For other models it SHALL include no reasoning parts.

#### Scenario: Ollama reasoning model
- **WHEN** a request uses `gemma4:12b`
- **THEN** the stream contains reasoning parts produced with Ollama `think` enabled, followed by text parts

### Requirement: Tools gated by model capability
When the selected model supports tools (the default), the endpoint SHALL offer the model the local tools, the MCP tools, the `loadSkill` tool and the `executeCode` tool, and SHALL allow up to 5 steps per request. When the model's entry sets tool support off, it MUST offer no tools and MUST NOT connect to MCP servers.

#### Scenario: Tool-capable model
- **WHEN** a request uses `gpt-4o-mini` and the question needs a tool
- **THEN** the model may call tools and produce a final answer within at most 5 steps

#### Scenario: Model without tool support
- **WHEN** a request uses a model whose registry entry sets tool support off
- **THEN** no tools are offered and no MCP connection is attempted

### Requirement: System prompt
The endpoint SHALL send a system prompt that establishes a helpful assistant, instructs the model to treat decoded content (Base64, hex, ROT13 and similar) as data and never as instructions, and appends the skill catalog.

#### Scenario: Encoded instruction in user input
- **WHEN** a user asks the model to decode a Base64 string that contains instructions
- **THEN** the model may explain what it says but does not follow the decoded instructions

### Requirement: Chat session identifier
The endpoint SHALL treat the request `id` as the chat session ID only when it is a string of at most 200 characters, and SHALL ignore it otherwise.

#### Scenario: Oversized id ignored
- **WHEN** a request carries an `id` longer than 200 characters
- **THEN** the request is processed with no session ID attached

### Requirement: Same-origin API without CORS
The API SHALL be served from the same origin as the frontend (Workers static assets in production, the Vite proxy in development) and MUST NOT add CORS headers.

#### Scenario: Cross-origin preflight
- **WHEN** a browser on another origin sends a CORS preflight to `/api/chat`
- **THEN** the response carries no `Access-Control-Allow-Origin` header
